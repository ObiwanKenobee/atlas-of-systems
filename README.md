# 🌍 Atlas Sanctum Frontend

> **The civilization interface for seeing, understanding, and acting on systemic reality.**

The backend intelligence engine is only half of Atlas Sanctum.

The harder problem is building the **civilization interface** through which humans, institutions, investors, governments, communities, and AI systems can understand complex reality and coordinate action.

The frontend determines whether Atlas becomes:

> **another dashboard**

or:

> **an operating system for structural resilience.**

Atlas Sanctum is designed to be the interface between people and the interconnected systems that shape their future.

---

# 🧭 The Current Paradigm

Most software presents civilization as disconnected information:

```text
Charts
Reports
Dashboards
KPIs
Maps
Tables
Alerts
```

The human is then expected to mentally reconstruct the system.

That approach breaks under sufficient complexity.

A person cannot simultaneously reason about:

* Climate
* Food
* Energy
* Infrastructure
* Finance
* Migration
* Governance
* Ecology
* Supply chains
* Social trust
* Knowledge

as independent dashboards.

The systems interact.

The frontend therefore has to represent **relationships, dependencies, trajectories, and consequences** rather than isolated metrics.

---

# 🌐 The Atlas Paradigm

Atlas should not merely show data.

It should show:

# **Reality as a Living System**

The visual references are conceptual rather than literal:

* Google Earth
* Palantir
* Civilization simulations
* Intelligent mission-control systems
* Ancient observatories
* Scientific instruments

The experience should feel like entering a system of observation and reasoning rather than opening an analytics application.

# 05 — 🔗 Cascade Explorer

This is where Atlas moves from observation toward systems reasoning.

The user selects a stressor or structural change.

Example:

> **Increase drought severity by 15% over 24 months.**

Atlas visualizes possible dependency pathways.

```text id="egv5i6"
DROUGHT
   ↓
AGRICULTURAL OUTPUT
   ↓
FOOD SUPPLY
   ↓
FOOD PRICES
   ↓
HOUSEHOLD PRESSURE
   ↓
MIGRATION
   ↓
URBAN DEMAND
   ↓
INFRASTRUCTURE PRESSURE
   ↓
FISCAL STRESS
```

Additional pathways may emerge:

```text id="ts9ks8"
Drought
  ├──► Agriculture
  │       └──► Food inflation
  │
  ├──► Hydropower
  │       └──► Energy costs
  │
  └──► Water availability
          └──► Urban pressure
```

The important concept is not deterministic prophecy.

It is **dependency visibility**.

The UI should clearly separate:

* Observed relationships
* Modeled relationships
* Scenario assumptions
* Possible downstream effects

# 📐 Reality / Model Separation

The interface must visually distinguish four states.

## Observed

Measured or reported information.

## Inferred

Model-derived interpretation.

## Simulated

Conditional future under specific assumptions.

## Recommended

Potential action derived from the preceding evidence and analysis.

Example:

```text id="hqy0rj"
OBSERVED
Reservoir level declining

        ↓

INFERRED
Water stress increasing

        ↓

SIMULATED
Potential 12-month supply pressure

        ↓

RECOMMENDED
Evaluate additional water-storage options
```

This distinction is foundational to trust.

# 🧠 Frontend State Model

The system will become too complex if every visualization owns its own version of reality.

Use centralized state for the shared interaction model.

```ts id="8r1a0z"
type AtlasState = {
  geography: Geography | null
  activeLayers: string[]
  selectedEntity: Entity | null
  selectedSignal: Signal | null
  selectedRisk: Risk | null
  timeline: TimelineState
  simulation: SimulationState
  intervention: InterventionState
  commandMode: CommandMode
}
```

All major surfaces should react to the same system state.

Select a region on the map:

**Health updates.**

Select a system layer:

**Graph updates.**

Move through time:

**Map updates.**

Run a scenario:

**Risks, pathways, and interventions update.**

The application should feel like **one instrument**, not twelve disconnected pages.

# 🧭 Design Doctrine

## Don't Show Everything

Reveal what matters at the current decision level.

## Show Relationships

A number becomes meaningful when its dependencies are visible.

## Show Trajectories

A single point rarely explains a system.

## Show Uncertainty

A model that hides uncertainty becomes misleading.

## Show Consequences

Recommendations should connect to possible outcomes.

## Preserve Context

Every decision should remain linked to its evidence and assumptions.

## Keep Human Authority

The system should expand human understanding, not silently replace judgment.

People do not necessarily need more information.

Show the dependency before the failure.

Show the trade-off before the decision.
